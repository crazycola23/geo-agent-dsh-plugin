# GEO 内部运营流程

## 目标与当前规格快照

此文档说明 Skill 如何按业务阶段调用 GEO；请求字段、方法、权限和幂等约束由自动生成的 [能力目录](capability-map.md) 提供。业务口径来自 `scrm-specs` 的决策单、`10-why/02-GEO业务规则说明.md` 和 OpenAPI。本实现目录对应 OpenAPI SHA-256：`6b7e1a2d785a7b337f4e0b967a64903981bc9e0574e9687580de874fa020a464`。

首版可在一个 DSH 会话中编排多个阶段，但仍保留业务人员的确认节点。它不启动定时检测或后台无人值守任务，也不代表 GEO、OneGl 或 Provider 已经通过真实账号端到端验收。

阶段间的裁决（确认事实、选择发布目标、发送检测、生成报告等）通过 DSH 内置的 `ask_user_question` 提交：候选项写成 options（label 用业务叫法，description 说明影响与代价），推荐项放第一并在 label 末尾加"(Recommended)"；得到答复前不推进该阶段。进度有两个入口随工具调用自动更新：会话里与「轨迹」同级的「GEO 进度」标签（显示当前会话流程条，`ask_user_question` 待答复时顶部出现横幅），以及左侧导航「GEO 工作台」页——操作者可随时查看 AI 做到了哪一步。

用户说「跑任务 / 开始跑单 / 继续运营 / 接手这个项目」时，按 [auto-run.md](auto-run.md) 的 OpsRun 协议整体推进：先只读感知项目现状（新项目走冷启动清单，存量项目续用既有策略与口径），产出运营决策单（动作 / 内容类型 / 平台 / 节奏 / 数据依据），经 `ask_user_question` 逐项审批后按依赖序执行。发布确认与资料上传的单独确认不因跑单模式豁免。

## 作业步骤

### 1. 明确项目和目标

- 用 GEO 只读接口确认用户指定的项目、客户、当前权限和已有记录；缺少项目 ID 时列出候选并请用户选择。
- 托管场景下项目或其归属客户尚未建立时：先 `get_customers` 查客户主体，必要时用 `post_customers` 建客户主体，再用 `post_projects` 建项目草稿。**客户名称就是生成链路里的品牌主体**，必须与资料所述品牌一致，否则稿件会把品牌能力写到错误主体上（见「本版覆盖边界」）。两项都要求令牌具备 `geo:project:create`。
- 先核对已有资料、事实、搜索问题、文章、媒体、发布记录、检测运行和报告，避免重复创建。
- 将“检查状态”“整理资料”“生成内容”“发布”“发起检测”“生成/比较报告”视为不同目标。没有明确要求的阶段不自动执行。

### 2. 登记资料

- `geo_list_evidence_files` 只列出投递目录里 `.doc`、`.docx`、`.pdf`、`.txt` 文件名和大小，不读取正文。
- 用户明确选择文件和项目后，调用 `geo_upload_evidence`。该工具限定在配置目录的直接子文件，拒绝绝对路径、路径穿越、符号链接和其他扩展名；DSH 会在上传前询问操作员。
- 上传后读取 GEO 资料记录和解析状态。文件扩展名、解析状态不能代替资料授权或事实确认；来源与公开准入遵循 `BR-FACT-001`、`BR-FACT-005`、`BR-FACT-006`。
- 若上传或解析结果未知，先查资料列表和记录。不要另换幂等键重新上传。

### 3. 提取并确认事实

- 仅使用 GEO 已有事实提取接口生成候选；向用户展示候选表述、来源资料、可验证摘录、适用范围和公开边界。
- 等用户逐项确认、编辑或驳回后，才调用相应事实写接口。AI 候选不能直接成为已确认事实；确认后仍须符合 `BR-FACT-001` 至 `BR-FACT-009`。
- 事实的公开边界不明确、来源不可访问、候选摘录无法在本次资料中定位，或存在冲突时，停止相关事实及依赖它的内容生成。

### 4. 准备问题与内容要素

- Query Research 和问题发散结果保持 `candidate`。按 `BR-QUESTION-007`、`BR-DETECT-017` 与 `T-OPEN-30` 展示候选，等用户勾选、编辑、删除或补充并确认；不得自动启用或发起检测。
- 内容要素提炼只能基于符合 `BR-CONTENT-016` 的已批准事实。不能因为资料上传成功或事实提取任务完成，就把原文直接交给要素提炼。
- 新建、编辑、冻结问题或内容要素前，查看当前版本、权限、状态和 OpenAPI 参数；每次写入仍需 DSH 操作员批准。

### 5. 生成文章

- 根据用户确认的问题、已批准事实和文章要求创建任务，再按 GEO 接口执行生成并读取实际产物。不得把 AI 质检结果表述为事实已验证或人工已审阅。
- 新生产路径的文章默认启用，不存在旧的提交审核、批准、驳回流程（`D-13`、`BR-CONTENT-017`）。不要人为构造旧审核状态。
- 按 `BR-CONTENT-021` 保留部分成功；失败槽位不由 Skill 自动重试。向用户报告成功文章与失败槽位，让用户决定是否按规则发起新的人工操作。
- 附图或视频可使用项目媒体库中已存在的素材，并由 GEO 合同内的绑定接口处理。**新增图片/视频上传经过 Resource/OSS，不在本 GEO OpenAPI 工具覆盖范围；需由运营人员在 GEO 界面完成上传和命名后，再由 Skill 读取、绑定或关联。**不得猜测或直连未纳入 GEO 合同的上传接口。
- 稿件产出后可用 `geo_export_article` 把正文导出成导出目录里的 .md 文件，供运营员在本地查看与修订（缺省导出该项目最新一篇）。**导出目录默认落在 DSH 数据目录（`DSH_HOME`，缺省 `~/.dsh`）下的 `geo-articles`**：随主机解析、首次导出自动创建，不硬编码任何机器路径；可用设置卡的「文章导出目录」或 `GEO_EXPORT_DIRECTORY` 覆盖。导出只读 GEO、只写本地文件，因此不弹 GEO 审批；紧的是导出目录本身——绝对路径、子目录、路径穿越与符号链接目标一律拒绝。正文缺失或超出单次读取上限时宁可拒绝，也不落半截稿子。**本地文件只是工作副本，正文以 GEO 记录为准**；按意见改完要回写 GEO，用 `put_article_versions_by_id`（会生成新版本，需带父稿件 version）。图片按**依赖 OSS 直链**处理：加 `includeGalleryImages: true` 时把项目图库图片以直链写进导出的「素材图片」一节，**不下载副本**；链接有效期以对象存储为准，正文文字不依赖链接。新增图片上传仍走 GEO 界面，不在本工具覆盖范围。

### 6. 发布（高风险、可选）

- 只有用户明确要求发布时才进入本阶段。先读取稿件版本、启用状态、目标资源和当前可用报价，创建当前发布预览。
- 给用户展示准确的稿件版本、发布目标、预览报价、预计费用、不可撤回或其他影响；等待用户明确确认后才调用发布确认接口。DSH 还会再询问一次操作员。
- 遵循 `BR-PUBLISH-001`、`BR-PUBLISH-004`、`BR-PUBLISH-005`。报价或稿件版本改变后重新预览；不得沿用过期报价。
- 发布结果未知时，使用原幂等键查本地记录、外部订单或内容指纹。未核实前不得重发，也不能把未知说成失败或成功。

#### 6a. 内容注入（T-OPEN-42，与媒介代发是两套事实）

把稿件正文填入客户自己的平台编辑器，由人在平台页面点下发布。它与 PublishRecord **不是一回事**：本域不欠预算、无外部订单号、无申诉与退款语义，不得与媒介代发互相换算或合并计数。

- **只能由人发起**（契约 N-10）：`post_injection_tasks` 这类写接口的权限码不进入项目令牌的允许范围，模型侧根本调不到；插件也把注入写入单列为「始终人工」。智能体的职责是给人准备材料（稿件就绪状态、平台账号、封面图、待注入文案），**不是**代替人发起注入。
- 只读查询可用：`get_injection_tasks` 按 (稿件, 平台账号) 看注入状态，`get_injection_hosts` 看哪些本机已配对。这两项**不表示**平台已发布——`injected` 只说明内容已填入编辑器，最终发布由人在平台页面完成。
- 事后的 `post_injection_tasks_confirm` / `cancel` 同样必须由人操作。
- 人要在本机驱动注入时，走 GEO 界面完成**本机配对**（`geo:injection:pair`，每台主机一次）。配对只签发本机驱动器身份，**不含任何平台登录凭据**——客户登录态留在本机浏览器资料目录里，GEO 不读取、不保存、不判定。
- 汇报口径：注入状态用「内容已填入平台编辑器」「人已声明发布」这类事实描述，**不得**写成「已发布」。

### 7. 检测（用户显式发起）

- 仅当用户明确要求本次检测时进入本阶段。展示确认后的问题快照、平台范围和接口返回的可用信息；依 `BR-DETECT-017`、`BR-DETECT-018`、`T-OPEN-30` 再向用户确认发送。
- GEO 检测必须由用户显式提交；后台只可推进已受理运行。不得启用定时/周期检测或自动创建新运行（`BR-DETECT-023`、`T-OPEN-39`）。
- 结果部分成功、失败、取消、跳过或未测量时分别报告。`ready`、任务终态或有响应都不能被用来推断分析完整度或指标为 0；指标保护遵循 `BR-DETECT-010`、`BR-REPORT-010`、`T-OPEN-13` 与 `G-19`～`G-23`。
- 失败是否可重试取决于 GEO 当前接口结果和 `BR-DETECT-004`；超时、未知、未确认退款时只查单或停在人工处理，不自动创建新 Attempt。

### 8. 生成或比较报告（用户显式操作）

- OneGl 客户 GEO 报告只在用户明确要求时生成；比较只在用户明确指定同一项目的两份已就绪快照时执行（`BR-REPORT-014`、`T-OPEN-39`）。生成与比较均由操作员发起，不是后台自动补做步骤。
- 读取报告关联的 `oneglTaskGroupId`，使用与该报告相同的平台范围。依 `G-34`，`GET /run-reports/{runId}` 不带 `runExecutionId` 表示整次运行全部平台；历史报告关联字段为空时必须披露退回全平台口径，不能宣称与局部客户报告一致。
- 分开说明采集状态、分析状态、报告可读状态和缺失范围。OneGl 外部报告不是 GEO `ReportRevision`；本工具不提供客户外发，也不生成 AI 叙事。
- 报告请求未知时先查本地报告关联和运行记录。仅在规格允许的恢复条件满足时，用已持久化的原请求与原幂等键恢复；不得新建检测或替换历史关联。

## 规格未决与禁止推断

- `T-OPEN-13` 仍未关闭；`G-19`～`G-23` 覆盖 GEO 指标公式、面板可比、真实 Provider 合同、Audit 阈值和 Strategy Outcome。不得用 LLM 计算指标、以 0 代替 N/A，或把外部快照包装成正式 GEO 指标。
- GEO 规格中的未决项或文档冲突不能由 Skill 自行裁定；停在依赖该口径的动作之前，明确指出具体 ID 并请求业务负责人处理。
- capability map 中的非 GET 操作都由 DSH 逐次询问；这不替代事实确认、检测发送或发布/费用确认。

## 本版覆盖边界

- DSH 工具目录当前纳入 153 个 GEO OpenAPI 操作、排除 68 个；完整范围和排除原因以自动生成的 [capability-map.md](capability-map.md) 为准。
- 内容注入域（T-OPEN-42，2026-10-08 进契约）**刻意只放行两个只读查询**：`get_injection_tasks` 与 `get_injection_hosts`。写接口（发起注入、声明发布、取消、本机配对）的权限码不进入项目令牌允许范围，因为契约要求注入必须由人发起——工具看不到它正是这条纪律的落实，不是缺陷。
- 托管能力（2026-10-07 纳入）：创建项目（`POST /projects`）与客户主体维护（`POST`/`GET /customers`）共用 `geo:project:create`。项目令牌须具备该权限码，否则工具可见但 GEO 侧仍会拒绝；客户名称是生成链路里品牌主体的来源，客户主体不符会让稿件把品牌能力写到错误主体上。
- 证据文件可由受限上传工具直接提交；图片/视频 Resource/OSS 上传仍在 GEO 界面完成。
- 不运行后台定时作业，不绕过 GEO 登录、权限、成本控制和 DSH 审批，也不调用任意主机或拼接任意 HTTP 请求。
